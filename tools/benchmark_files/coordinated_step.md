# Согласованное выполнение шага бенчмарка

Подготовительная серверная часть: BenchmarkRunStep согласует BenchmarkRunJournal и вызываемый файловый исполнитель. HTTP, SQL-аутентификация и интерфейс ещё не подключены. Это не завершение PERF-ADMIN-01.

## Проверка в Windows

Из корня репозитория после получения коммита:

```powershell
powershell.exe -NoProfile -File .\tools\Test-BenchmarkRunStep.ps1
if ($LASTEXITCODE -ne 0) { throw 'Проверки совместного шага завершились ошибкой; остановка' }
```

Ожидаемый вывод: PASS: 10/10 coordinated-step groups; CLR ...

Скрипт совместно компилирует три настоящих модуля и обвязку в новом процессе Windows PowerShell, создаёт уникальный временный каталог .wvs-* внутри рабочей копии и удаляет его в finally без перехода по reparse points. Рабочий DataRoot не читается. Скрипт сохранён в UTF-8 с BOM для русского текста в Windows PowerShell. Ассистент не выполнял этот Windows-прогон. Прежние отдельные результаты12/12 и13/13 не заменяют интеграционную проверку.

## Порядок выполнения

Execute сначала проверяет переданный callback полномочий, затем держит исключительную operation.lock в каталоге журнала до окончания шага. Под этой блокировкой выполняются Begin → проверяемая файловая операция → проверка результата и очистки → Complete → финальная проверка полномочий/срока. Callback операции и полномочий задаются доверенным серверным кодом, не JSON пользователя.

Операция получает callback контрольной точки: он повторно проверяет полномочия, читает журнал с диска и проверяет фазу1, номер текущего шага и срок действия. Перед Complete проверяются CleanupConfirmed, число псевдохранилищ, размер файла, число проверенных чтений и конечное неотрицательное время. Поля результата являются контрактом доверенного исполнителя, а не доказательством произвольного клиентского отчёта.

Ошибка до Complete оставляет в журнале фазу выполнения без увеличения next; такой шаг нельзя повторить. Если Complete уже записан, но финальная проверка или передача ответа не удалась, next может быть увеличен: состояние требуется прочитать заново, неопределённое клиентское время отбросить, откат или повтор файловой операции не выполнять.

StopAndConfirm использует ту же operation.lock, затем Stop и ConfirmCleanup. Если операция ещё занята, остановка получает отказ блокировки, а не удаляет файлы параллельно записи. Callback проверки отсутствия файлов обязателен; этот метод сам ничего не удаляет. Отзыв отдельного права не отменяет требование аутентификации прежней сессии для остановки/подтверждения. В рабочем маршруте пустые callback запрещены.

## Границы совместного теста

Проверяются настоящий файловый цикл и сохранность контрольных vaults/history, сохранение журнала, два последовательных шага, отказ повторного/чужого шага, конфликт остановки с выполняющейся операцией, прерывание без повтора, отзыв полномочий, отклонение неподтверждённого результата, отказ ложного подтверждения очистки и поздний результат.

Для этой проверки старое BenchmarkFileCycle.Execute создаёт отдельный временный GUID-каталог рядом с GUID-каталогом журнала внутри тестового Bench; callback проверяет отсутствие таких файловых каталогов после цикла. Возвращаемый Result.RunId относится к файловому вызову, а не к идентификатору журнала. Сохраняемая связь этих каталогов пока не реализована: нельзя использовать такую тестовую схему как готовую схему восстановления после сбоя IIS.

## Остаток

До HTTP нужны единая сохраняемая привязка запроса/журнала/тестовых файлов, общий порядок блокировок, квоты и ограниченная очистка остатков, настоящий адаптер сессии/поколения права. Все пути определяет сервер и проверяет принадлежность DataRoot/Bench; вспомогательный модуль не заменяет эту проверку. Прямые вызовы журнала не должны обходить блокировку выполняющейся операции в будущем маршруте. Нет автоматического восстановления процесса, фоновой очистки, истории результатов или проверки нескольких настоящих пользователей. В этом пакете существующие модули, SQL, конфигурация и bundle не меняются.
