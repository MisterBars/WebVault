# Основа изолированного файлового цикла бенчмарка

Статус: подготовительный код, не подключённый к HTTP или экрану бенчмарка. Для отдельной проверки не нужны миграция SQL, изменение конфигурации, сборка bundle или публикация сайта. Это не завершённая задача PERF-ADMIN-01.

<a id="run-on-windows"></a>

## Запуск в Windows

Из корня репозитория запустите новый процесс Windows PowerShell с .NET Framework4.5 или новее:

```powershell
powershell.exe -NoProfile -File .\tools\Test-BenchmarkFileCycle.ps1
if ($LASTEXITCODE -ne 0) { throw 'File-cycle checks failed; stop' }
```

Если выполнение скрипта заблокировано, не ослабляйте политику выполнения вслепую. Скрипт совместно компилирует вспомогательный класс и тестовую обвязку, затем выполняет12 групп проверок в уникальном коротком каталоге .wvb-* внутри корня репозитория. Каталог удаляется в finally. Рабочий DataRoot из конфигурации не читается; сохранность проверяется по контрольным файлам в тестовых vaults/history. Ожидаемый вывод: PASS: 12/12 file-cycle groups. Ошибка компилятора или файловой системы означает провал проверки, а не разрешение продолжать публикацию.

До запуска тест проверяет длину пути самого длинного обычного тестового случая относительно неизменённого ограничения корня в100 символов. Дополнительная граничная группа требует успешной работы с корнем длиной100 символов и отказа для101 символа без создания Bench. Длинные системные временные пути для тестовых данных больше не используются. Если слишком длинен сам путь к рабочей копии, скрипт останавливается до создания тестовых данных и предлагает использовать более короткий путь. После принудительного завершения процесса уникальный тестовый каталог может остаться; не включайте его в коммит.

Ассистент не выполнял эту PowerShell/.NET-проверку. Node-тесты и просмотр в Python не подтверждают её результат. Гонки с junction/reparse points в Windows, принудительное завершение процесса, настоящие сессии IIS и целевая публикация остаются непроверенными.

<a id="foundation-contract"></a>

## Контракт файлового ядра

BenchmarkFileCycle.Execute принимает существующий проверенный DataRoot, actors (1–8), sizeKiB (1–64) и обязательный callback актуальной проверки полномочий. DataRoot/Bench создаётся только после успеха первоначальной проверки. Будущий HTTP-обработчик обязан проверить, что DataRoot находится вне сайта, и реализовать в callback проверки владельца, сессии и выданного права. Пустой callback используется только временной тестовой обвязкой, никогда рабочим HTTP-маршрутом.

Структура: Bench/<server-generated-runId>/owner.txt и vaults/actor-0001/note.md; во время замены используется update.tmp. Псевдопользователи представлены папками, а не записями auth.Users или независимыми авторизованными сессиями. Личный VaultId не регистрируется. В корне используются маркер фиксированного формата и исключительная блокировка root.lock; существующие данные Bench без маркера не принимаются под управление. Неизвестные записи в корне блокируют новый цикл. Разрешено до32 каталогов запусков, включая оставшиеся после сбоев. Каждый вызов синхронный, а файловая блокировка последовательно пропускает целые циклы всех запусков; это не нагрузочная проверка одновременных пользователей. При конфликте блокировки происходит отказ без ожидания или повторения изменяющих операций.

Цикл создаёт детерминированные ASCII-байты, читает и сравнивает все байты, повторно проверяет прежнее содержимое перед заменой, записывает и сбрасывает на диск новый временный файл, заменяет заметку без сохранения резервной версии в истории, проверяет новые байты и удаляет заметку. В результате указываются три проверенных чтения на псевдопользователя. CycleMs включает генерацию синтетического содержимого, создание каталогов псевдопользователей, файловый ввод-вывод, проверки результата и промежуточные вызовы проверки полномочий. Финальная очистка каталога запуска в это время не входит. Это не физическая задержка диска и не рабочий путь сохранения личной заметки.

Бюджет120 секунд проверяется в контрольных точках. Он не может принудительно прервать синхронный файловый вызов или callback проверки полномочий. Ошибка любого callback, операции, проверки содержимого или очистки исключает успешный результат. Очистка затрагивает только известные пути вновь созданного текущим вызовом запуска после проверки его маркера. Рекурсивное удаление каталога запуска не используется; неизвестные записи и reparse points приводят к отказу. После успешной очистки остаются только маркер управляемого корня и root.lock.

При завершении процесса или ошибке маркера/очистки оставшиеся каталоги продолжают учитываться в лимите. В самом файловом ядре нет автоматического восстановления оставшихся запусков, сохраняемых сведений о владельце/сессии, состояния между HTTP-запросами, устранения повторных запросов или фоновой очистки. Не подключайте ядро к HTTP до реализации и проверки этих защит. Корневая блокировка согласует взаимодействующие процессы, но не защищает от злонамеренного администратора ОС; права файловой системы остаются обязательными.

## Границы пакета

Пакет содержит файловое ядро, отдельную Windows-проверку компиляции/ввода-вывода и этот контракт. Остаток: сохраняемый протокол запросов/запусков, адаптер реальных полномочий, проверки границ и восстановления, согласование существующего транспорта с ядром (его прежний контракт синтетического содержимого требует согласования), HTTP-маршрут, интерфейс, целевая регрессия и обновление канонической документации, backlog и истории для подключённой функции. Этот Git-пакет не меняет существующие обработчики, SQL, рабочую конфигурацию или личные данные.
