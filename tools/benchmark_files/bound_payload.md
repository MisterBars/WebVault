# Привязанные тестовые файлы

Подготовительная серверная часть без HTTP/UI. ExecuteBound использует тот же файловый цикл и проверки, что Execute, но получает воспроизводимый ID файлового каталога из ID запуска журнала и номера шага. Старый Execute сохраняет случайный ID и прежний контракт.

## Формат привязки версии1

BoundId принимает непустой Guid запуска журнала и index0–103. Вычисляется SHA-256 UTF-8 строки WebVault.Bench.Payload.v1|<Guid в формате N>|<index десятичный invariant>. Первые16 байт преобразуются через new Guid(byte[]).ToString("N"). Порядок байтов Guid существенен: для11111111111111111111111111111111 и шага0 ожидается f539f58a4675e3c679e3ff8f903a9fde.

Каталог файлов — DataRoot/Bench/<BoundId>/vaults/actor-0001, журнал остаётся в своём соседнем GUID-каталоге. Связь вычисляется из сохраняемого Run журнала и номера шага и не зависит от памяти процесса. Это адресация, не право доступа, не секретный токен и не доказательство владельца. HTTP-адаптер обязан получать ID запуска/параметры только из проверенного журнала, проверять сессию и поколение права, а не принимать произвольный journalRun от клиента.

ExecuteBound нужно вызывать через BenchmarkRunStep.Execute. Уже существующий файловый каталог вызывает benchmark_collision: он не принимается под управление и не перезаписывается. После успешного удаления файлов только журнал запрещает повторное исполнение завершённого шага; прямой повтор ExecuteBound не является устранением повторных HTTP-запросов.

## Адресная очистка

RecoverBound вызывается после остановки журнала под operation.lock его запуска; callback подтверждает прежнюю действующую сессию, а не всё ещё выданное право бенчмарка. Проверяются управляемый корень Bench, root.lock, точный вычисленный каталог, маркер с ID/числом псевдохранилищ и известные пути. Отсутствующий каталог допустим, но отсутствующий/неуправляемый корень не создаётся ради очистки и не считается подтверждением.

Удаляются только известные объекты одного шага, без рекурсивного удаления неизвестного содержимого. Неизвестные файлы, неверный/недописанный маркер, reparse points и ошибки оставляют очистку неподтверждённой. Очистка может успеть удалить часть известных файлов до отказа; она не атомарна. Другие шаги и журнал не удаляются.

Для ConfirmCleanup всего запуска вызывающий код обязан сверить все допустимые шаги, а не только один index. Пока это выполняет тестовая обвязка; рабочего обработчика ещё нет. Нет фонового обхода, автоматического удаления повреждённых записей или восстановления неизвестных каталогов.

## Windows-проверки

После получения коммита из корня репозитория сначала новый тест, затем прежние регрессии; при любом провале остановиться:

```powershell
& {
    powershell.exe -NoProfile -File .\tools\Test-BenchmarkBoundPayload.ps1
    if ($LASTEXITCODE -ne 0) { throw 'Ошибка проверки привязанных файлов' }
    powershell.exe -NoProfile -File .\tools\Test-BenchmarkFileCycle.ps1
    if ($LASTEXITCODE -ne 0) { throw 'Ошибка регрессии файлового ядра' }
    powershell.exe -NoProfile -File .\tools\Test-BenchmarkRunJournal.ps1
    if ($LASTEXITCODE -ne 0) { throw 'Ошибка регрессии журнала' }
    powershell.exe -NoProfile -File .\tools\Test-BenchmarkRunStep.ps1
    if ($LASTEXITCODE -ne 0) { throw 'Ошибка регрессии совместного шага' }
}
```

Ожидаемые числа групп:10 bound-payload,12 file-cycle,13 run-journal,10 coordinated-step. Это план повторного запуска, не уже полученный результат нового коммита. Ассистент Windows-проверки не выполнял. Скрипт использует уникальный временный каталог .wvp-* внутри рабочей копии и не читает рабочую конфигурацию. Проверяются фиксированный формат привязки, два настоящих шага, запрет повтора, сохранённый остаток и его адресная очистка, отказ чужому владельцу, неизвестное содержимое, неверный маркер, коллизия, независимость шагов и отказ авторизации.

## Остаток до HTTP

Проверенный каталог журнала и поиск по requestId, квоты логических запусков и физических каталогов, реальные SQL/session/grant-проверки, восстановление при прерванной записи журнала/маркера, ограниченная очистка остатков без действующей пользовательской сессии, подключение транспорта и интерфейса. Тест моделирует остаток на диске, но не завершает IIS и не доказывает устойчивость к потере питания. Прежний совместный тест сохраняет случайную схему как регрессию; новая обвязка проверяет привязанный вариант.
