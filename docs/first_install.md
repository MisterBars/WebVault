# Новая установка WebVault

[Указатель](index.md) · [Сборка](npm_build.md) · [Получение исходников](github_transfer.md) · [Сессии](session_policy.md)

Основной вход — index.html: единое окно с модальными входом и настройками. Диагностика health требует вошедшего администратора и локального запроса с сервера; анонимного диагностического обхода нет. Инструкция описывает новую установку, а не перенос существующей БД/DataRoot.

## 1. IIS и файлы

Публиковать только согласованный состав src/WebVault.Web, включая отдельно собранный browser bundle; не корень с .git/docs/database/tools/node_modules. Создать WebVaultPool: CLR v4.0, Integrated, ApplicationPoolIdentity. Сайт связать именно с этим пулом. Пример физического пути: D:\project\WebVault\src\WebVault.Web; локальная HTTP-привязка 127.0.0.1:8085, свободный порт, имя узла пустое. Пулу нужны чтение/выполнение файлов сайта, не изменение:

```powershell
icacls 'D:\project\WebVault\src\WebVault.Web' /grant 'IIS AppPool\WebVaultPool:(OI)(CI)RX'
if ($LASTEXITCODE -ne 0) { throw 'Site ACL update failed; stop' }
```

Если используется другой физический путь, указать его в настройках IIS и ACL. Сборка и публикация сайта — отдельные действия; порядок проверок находится в npm_build.md.

## 2. БД: все скрипты 00–07

SSMS под администратором. Текущая схема доступа предполагает IIS и SQL Server на одной Windows-машине, Integrated Security и пул WebVaultPool. На новой установке выполнить последовательно все файлы из [database/install](../database/install), останавливаясь при ошибке:

| Порядок | Скрипт | Назначение |
| --- | --- | --- |
| 00 | [00_database.sql](../database/install/00_database.sql) | БД WebVault, базовые схемы; AUTO_CLOSE/AUTO_SHRINK выключены, recovery model существующей БД не меняется. |
| 01 | [01_grant_apppool_access.sql](../database/install/01_grant_apppool_access.sql) | Windows login/user пула, роль webvault_app и CONNECT; без db_owner. |
| 02 | [02_auth.sql](../database/install/02_auth.sql) | Users/UserSessions и объектные разрешения; аккаунты/пароли/сессии скрипт не создаёт. |
| 03 | [03_user_lifecycle.sql](../database/install/03_user_lifecycle.sql) | DeletedUtc для мягкого удаления. |
| 04 | [04_user_management.sql](../database/install/04_user_management.sql) | Объектное разрешение DELETE на auth.Users для явного полного удаления. |
| 05 | [05_user_vaults.sql](../database/install/05_user_vaults.sql) | storage.UserVaults и связь с владельцем. |
| 06 | [06_account_security.sql](../database/install/06_account_security.sql) | MustChangePassword и журнал PasswordResetEvents; существующие аккаунты получают флаг 0, пароли не меняются. |
| 07 | [07_folders_and_purge.sql](../database/install/07_folders_and_purge.sql) | PurgeJobs, проверка зависимой схемы и разрешения для отдельной операции удаления владельца с файлами. |

Скрипты 04/07 сами пользователей или файлы не удаляют. FK не отключать, db_owner приложению не выдавать. На обновлении применять только подтверждённо неприменённые миграции после бэкапа БД и DataRoot; не повторять первоначальную настройку администратора. Обновление кода согласовывать с миграциями при отсутствии активной работы: новый код может требовать новых столбцов/таблиц.

Прежняя инструкция содержит ограничение «не изменять ВВТ». Его расшифровка в проверенных SQL не установлена; это открытый вопрос ревизии, не разрешение менять неизвестный объект.

## 3. Данные и конфигурация

```powershell
New-Item -ItemType Directory -Force -Path 'D:\WebVaultData\vaults','D:\WebVaultData\history' -ErrorAction Stop
icacls 'D:\WebVaultData' /grant 'IIS AppPool\WebVaultPool:(OI)(CI)M'
if ($LASTEXITCODE -ne 0) { throw 'DataRoot ACL update failed; stop' }
```

Проверить все ACL: grant не удаляет доступ других Windows-пользователей. DataRoot должен быть вне сайта, на обычном локальном диске, не junction/symlink/UNC; не допускать недоверенных сторонних писателей. Реальные заметки не переносить единственной копией и не использовать как единственные данные испытаний.

Для новой установки скопировать [Web.config.example](../src/WebVault.Web/Web.config.example) в Web.config рядом. При обновлении сохранить рабочий файл и согласовать необходимые изменения, не заменять его шаблоном. Строка подключения — к экземпляру этой машины, Database=WebVault, Integrated Security=True. В одной секции appSettings: AdminSetupEnabled=false, AdminSetupKey пусто, DataRoot=D:\WebVaultData. Секреты и рабочий Web.config не коммитить.

## 4. Ключ и первый администратор

Сгенерировать временный ключ в PowerShell:

```powershell
$bytes = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
$rng.Dispose()
[Convert]::ToBase64String($bytes)
```

44-символьный Base64 — ключ первоначальной настройки, не пароль. Не отправлять в чат/Git. В рабочем Web.config временно установить AdminSetupEnabled=true маленькими буквами, AdminSetupKey=полученная строка.

Открыть http://127.0.0.1:8085/index.html на сервере; в модальном входе раскрыть создание первого администратора. Ввести ключ, логин (3–64 латиница/цифры/точка/дефис/подчёркивание), имя, пароль 15–128 и повтор. После успеха сразу выключить AdminSetupEnabled=false и очистить ключ, затем войти.

[SetupStatusHandler](../src/WebVault.Web/App_Code/SetupStatusHandler.cs) разрешает показ настройки только при локальном запросе, точном значении true, ключе не короче 40 символов и отсутствии любых записей в auth.Users. Наличие пользователя — основание входить/восстанавливать доступ, не обходить проверку и не создавать первого администратора заново.

До инициализации проверять IIS/SSMS и ответ api/auth/setup_status.ashx. canSetup=true означает выполненные условия показа формы в момент запроса, не резервирование первого создания. canSetup=false не доказывает доступность БД: вне условий локального включённого setup запрос к таблице может не выполняться. Ошибку статуса не трактовать как разрешение создать пользователя вручную.

[Health](API_OVERVIEW.md#диагностика-health) доступен только вошедшему локальному администратору. Даже без check=db он проверяет сессию через БД; aspnet:ok/database:not_checked не независимая проверка ASP.NET без SQL. check=db добавляет SELECT DB_NAME и сверку имени WebVault, не полную проверку схемы/миграций/ACL. Точные ответы, порядок guards, таймаут и503 — в каноническом API-контракте.

### Порядок диагностической проверки

Ниже процедура для установки, не результаты этой редакции:

1. До первого администратора проверить физический путь/пул/доступ к файлам, успешное выполнение SQL00–07 и локальный setup_status. Не ожидать успешный health без сессии и не отключать его авторизацию для проверки ASP.NET. При не-JSON/404/ошибке IIS сначала сверить опубликованный путь и конфигурацию; при ошибке миграции остановиться.
2. После создания отключить setup/очистить ключ, войти администратором на том же origin и получить действительную сессию. Сначала открыть health без check=db, затем с check=db в том же профиле локально на сервере. Записать отдельно HTTP-код и безопасные поля ответа, не cookies/CSRF/пароли.
3. При401 проверить вход/срок сессии и origin, а не переустанавливать БД. При403 проверить конкретный код/роль/forced change/локальность/HTTPS. При503 database_check_failed остановить приёмку и сохранить errorId: причина может находиться в сессионном SQL до дополнительной проверки БД. Не выдавать db_owner, не отключать FK/guards и не пересоздавать DataRoot ради зелёного health.
4. Два успешных ответа health разрешают перейти к функциональным испытаниям следующего раздела, но не закрывают их. Отдельно подтвердить SQL-миграции/объектные права, ACL и чтение/сохранение тестовых файлов; успешный health не заменяет проверку резервного восстановления и сетевого HTTPS.

## 5. Начало работы и проверка

Администратор открывает административное меню/диагностику и создаёт обычную личную учётку по [руководству пользователей](user_management.md). Выйти через ribbon, войти личной учёткой в той же модалке, создать хранилище и тестовую заметку, сохранить/перечитать. Шестерёнка открывает модальные настройки и смену своего пароля. Контракты собственного ника/пароля и сессий — в [session_policy.md](session_policy.md); для временного пароля действует [ограниченный вход и обязательная смена](session_policy.md#ограниченный-вход-и-форма), подробности административного сброса — в [том же руководстве](session_policy.md#административный-временный-пароль).

Отдельно проверить загрузку browser bundle, режимы редактора, ввод, историю и автосохранение по [инструкции сборки](npm_build.md). Наличие страницы или успешный SQL не доказывает работу редактора. Windows 7/.NET Framework 4.5/Firefox 113 проверять на целевом ПК; системные компоненты на нём не скачивать. Эта редактура не является результатом установки или тестов IIS/SQL/браузера.

## Ошибки, удаление и перенос

- setup_disabled: проверить точное true и длину ключа; setup_key_rejected: сверить ключ; already_initialized: использовать вход, не повторять setup.
- SQL сообщает DefaultAppPool: проверить фактически назначенный пул и Windows login/user БД.
- Диагностика health:401 не результат проверки DB_NAME,403 требует сверки кода guards,503/errorId не доказательство только ошибки имени БД. Не продолжать приёмку при необъяснённом отказе.
- При потере ответа setup не повторять создание вслепую: сверить setup_status и возможность входа; при неясном результате разбирать ошибку без ручной вставки администратора.
- user_changed_reload_list: обновить список пользователей и повторно проверить цель.
- user_has_dependencies у старого user_manage purge: операция не удаляет владельца хранилища. Не обходить FK и не считать это универсальным запретом отдельного purge_user.
- Отдельный purge_user — необратимая операция с файлами после мягкого удаления и подтверждения; см. [folders_and_purge.md](folders_and_purge.md). SQL и файлы не образуют общей атомарной транзакции, сбой может оставить частичную очистку. Для установки выполнять purge не требуется.
- 429: соблюдать лимит, не отключать защиту наугад.

Перенос существующих данных требует согласованных бэкапов БД/файлов/настроек и отдельного регламента восстановления. После восстановления проверить login/user пула на новой машине и отозвать старые сессии; setup заново не запускать. Независимые установки не синхронизируются автоматически. Сетевое размещение требует HTTPS и отдельной проверки. Источники через Git и рабочие данные переносятся раздельно.
