# Папки и полное удаление владельца с файлами

## Область и статус

Подробный контракт административного удаления владельца с зарегистрированным хранилищем. База документальной сверки —94276d3e9929f819039995c58098368a175fa251; сопоставлены PurgeUserHandler.cs/application.js, ранее прочитанные VaultHandler.cs/файловые модули, database/install/07_folders_and_purge.sql и руководство управления пользователями. Это статическая сверка, не новый запуск SQL/C#/IIS/браузера и не приёмка установленного сайта.

Папки/дерево/ПКМ/move/rename/корзина/автосохранение имеют реализацию в сверенных исходниках; прежнее «следующий этап» не текущий общий статус проекта. Канонический файловый контракт —file_vault.md, механизм сохранения —editor_autosave.md. Наличие этих функций не закрывает весь clipboard, историю после rename/move, все сценарии восстановления или регрессию.

## Установка

Сохранить черновики и локальные изменения, сделать согласованный бэкап БД WebVault и DataRoot(vaults/history), а не только исходников. Выполнять только подтверждённо неприменённые миграции по first_install.md. database/install/07_folders_and_purge.sql предназначен для запуска администратором после00–06, проверяет наличие storage.UserVaults; это не команда заново применить уже установленную07.

Скрипт создаёт storage.PurgeJobs, предоставляет webvault_app SELECT/INSERT/UPDATE на журнал и DELETE на storage.UserVaults, устанавливает storage.AssertPurgeSchema и разрешает её EXECUTE. Он сам не удаляет пользователей/файлы, не отключает FK и не выдаёт db_owner. Рабочие Web.config/DataRoot сохраняются; права пула Modify должны быть настроены отдельно с проверкой ACL. После функционального обновления публикуется согласованный комплект и выполняется Ctrl+F5; docs-only не требует SQL/сборки/публикации.

## Папки и заметки

Вложенные .md и папки обслуживаются существующим vault.ashx. GET action=list&folder=Работа/Серверы возвращает folder/files/folders с полными относительными путями. POST mkdir с name=Работа/Серверы требует существующего родителя, не создаёт цепочку молча. name корневой заметки остаётся допустимым; GET read и POST create/save поддерживают относительные компоненты через /. Прежнее объединение read с POST в описании API не означает поддержку этого метода.

Ограничения:16 компонентов,180 символов относительного пути,100 в компоненте,240 полного пути,500 нескрытых non-reparse элементов каталога, заметка256 KiB/131072 UTF-16 единицы при записи. Другие обычные файлы не показываются редактируемыми заметками, но учитываются лимитом listing. Абсолютные/backslash/пустые/скрытые/.. и зарезервированные компоненты запрещены, проверяются каждый существующий компонент/reparse и граница корня.

Текущее дерево/выбор, сохранение dirty-буфера перед файловыми действиями и заголовок с относительным путём —[file_vault.md](file_vault.md#дерево-выбор-и-меню). Старые кнопки «На уровень выше» и отдельный список подпапок относятся к первоначальной навигации, не замена современному дереву. История остаётся предыдущими .md-копиями без стабильного ID/сопоставления пути после rename/move и полноценного интерфейса восстановления; это отдельная задача, не причина объявлять move отсутствующим.

## Полное удаление

Не смешивать три операции:purge записи корзины заметок, совместимый SQL-purge пользователя и административную очистку владельца с файлами. Старый user_manage purge не очищает зарегистрированное хранилище; его FK/notes-ограничения описаны в user_management.md. Текущий application.js направляет действие «Удалить вместе с заметками» в отдельный api/admin/purge_user.ashx.

Только действующий активный неудалённый администратор без MustChangePassword; свою и любую административную цель удалить нельзя. Цель предварительно мягко удалена и неактивна. UI предупреждает об уничтожении всех заметок/вложенных папок/файлов в каталоге владельца, истории и сессий; ввести точный текущий логин. Это необратимое действие на отдельной тестовой учётке/копии данных, не на единственной копии настоящих заметок.

POST JSON:userId,rowVersion,confirmationLogin,deleteFiles=true, сессия/X-WebVault-Request/CSRF. rowVersion —Base64 ровно8 байтов. Путь не принимается из браузера: VaultId определяется через storage.UserVaults, каталог —по DataRoot и GUID N. Проверки цели до начала/при продолжении требуют точный Ordinal-логин, версию, мягкое удаление, отсутствие административной роли. Ошибки формата/подтверждения/прав не разрешают обход защит.

## Журнал и стадии

storage.PurgeJobs:JobId(GUID PK), уникальный TargetUserId, ActorUserId, nullable VaultId/RootHash(binary32), Status(Started/RetryRequired/Complete), LastError(varchar80), CreatedUtc/UpdatedUtc(datetime2(3)). Журнал хранит ID, хеш корня, тип ошибки и время, не тексты заметок/пароли; FK на удаляемого пользователя намеренно нет. В сверенной панели нет отдельного полноценного обозревателя заданий: при ошибке приходит errorId, администратор может сверить запись в SSMS. Это не утверждение о выполненной ручной диагностике.

1. Первая SQL-транзакция повторно проверяет инициатора, цель/RowVersion/логин/связь с GUID и схему. До файлового удаления фиксирует задание Started. Для vault вычисляется RootHash из канонического DataRoot без учёта регистра; для цели без vault корень не требуется.
2. Вторая транзакция блокирует инициатора/цель/задание/реестр, повторно проверяет права, цель, связь и схему. До удаления полностью обходит оба каталога, затем удаляет только DataRoot/vaults/<GUID N> и DataRoot/history/<GUID N>. Вложенная корзина и служебные файлы внутри каталога владельца входят в эту очистку, в отличие от отдельных действий корзины, которые не чистят history.
3. После успешной очистки ещё раз проверяет администратора, удаляет auth.UserSessions/storage.UserVaults/auth.Users и фиксирует Complete в одной SQL-транзакции. Первое успешное выполнение означает завершённую очистку этих каталогов и SQL-записей; логин освобождается.

Аудит reset, сам журнал purge, внешние бэкапы и копии вне этих каталогов не очищаются. Безопасное стирание носителя и уничтожение всех внешних персональных данных не обещаны.

## Сбои и повтор

SQL и ФС не одна атомарная транзакция. После подтверждения ошибка может оставить частично удалённые файлы, даже когда SQL-удаление учётки/реестра откатилось. Мягко удалённая цель остаётся, задание Started/RetryRequired; повтор после устранения причины продолжает необратимую очистку, не восстанавливает файлы. Два запроса этого обработчика сериализуются блокировками цели/задания.

При обрыве процесса Started остаётся. Недоступная БД может помешать записать последнюю ошибку, но зафиксированное начальное задание сохраняется. RootHash и VaultId запрещают продолжать незавершённое задание на другом DataRoot/реестре; корень и связь при pending не менять. Отсутствующие уже удалённые каталоги при повторе допускаются. Незарегистрированные сироты после старого сбоя init не присваиваются пользователю наугад.

После потерянного ответа при Complete повтор того же TargetUserId возвращает завершённое задание, не запускает удаление по повторно занятому логину. Синтаксические проверки входа/rowVersion/deleteFiles и проверка администратора сохраняются; ранний возврат Complete не является новой сверкой существования/логина уже удалённой цели. Старый UserId вручную новому пользователю не назначать.

Ошибки после получения jobId возвращают errorId; обработчик пытается записать RetryRequired/тип исключения, не перезаписывая Complete.403/409 или503 не считать доказательством отсутствия файловых изменений. Сначала сверить задание/состояние каталогов, затем осознанный повтор; FK/лимиты/ACL не отключать ради ложного успеха.

## Схема, обход и лимиты

storage.AssertPurgeSchema выполняется WITH EXECUTE AS OWNER для проверки метаданных FK. Разрешены известные зависимости auth.UserSessions/storage.UserVaults от auth.Users; иные FK на Users и любые FK на UserSessions/UserVaults блокируют текущую очистку. При добавлении таблиц сначала согласовать процедуру и очистку, не расширять whitelist без переноса данных/проверок. FK не отключаются.

Preflight и удаление используют один Stopwatch с бюджетом около20 секунд на попытку, не по20 секунд на каждый каталог. До10000 узлов суммарно двух деревьев, глубина до24 от корня обхода, путь до240 символов. Проверяются reparse и предки каталогов; при удалении атрибуты проверяются повторно, перехода по ссылкам нет. Превышение лимита/отказ доступа не выдаются за успех.

Гарантии предполагают обычные локальные каталоги, корректные ACL и отсутствие недоверенных сторонних писателей. Junction/symlink/чужие hard links и изменение дерева извне не входят в обещание атомарной защиты. Большие неподдерживаемые деревья требуют отдельного доработанного процесса, не снятия защит. Цель без vault может удаляться без настроенного DataRoot; наличие обычного пользовательского реестра нельзя обходить ручным удалением записи.

## Тесты

Все пункты —план на отдельных тестовых учётках/копиях, не отчёт нового успешного прогона:

- [ ] Подтверждённо установлена07 и прежние учётки/пароли/сессии работают; установка сама не удаляет данные.
- [ ] Работа/Серверы и вложенный .md создаются/сохраняются/читаются; переходы дерева/корня не теряют открытый текст.
- [ ] Две обычные учётки с одинаковыми папками изолированы; ../, чужой GUID, reparse и недопустимые пути не обходят владельца.
- [ ] Только отдельная мягко удалённая тестовая цель с вложенными файлами/history удаляется; соседние каталоги нетронуты.
- [ ] После первого успеха нет Users/UserSessions/UserVaults и обоих каталогов цели, задание Complete; аудит/бэкапы/журнал сохраняются.
- [ ] Неверный логин/RowVersion, не мягко удалённая цель, обычная роль, себя/админа и неверный CSRF не разрешают начало очистки.
- [ ] Заблокированный файл/частичный отказ:нет ложного успеха, цель/реестр остаются; после устранения причины осознанный повтор завершает очистку.
- [ ] Обрыв процесса/БД и Started/RetryRequired, RootHash/VaultId-конфликт, неизвестные FK и пределы дерева корректно останавливают/ограничивают операцию.
- [ ] Reparse в тестовом дереве блокирует preflight, внешний каталог не тронут; проверяются и предки.
- [ ] Потерянный ответ/повтор Complete не удаляет данные нового пользователя с тем же логином.
- [ ] Цель без vault не требует DataRoot; ограниченная временная сессия не получает личное файловое/административное API.
