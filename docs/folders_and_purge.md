# Папки и полное удаление с файлами — комплект 07

Статус: код подготовлен, IIS/браузер/SQL ещё не проверены. Не использовать единственную копию настоящих заметок для испытаний. Поддержка контекстного меню/копирования/перемещения/корзины/undo/автосохранения этим комплектом НЕ реализована; это следующий этап.

## Установка
Сохранить черновики. Сделать бэкап БД WebVault И DataRoot (vaults/history), а не только исходников. Получить файлы без сброса локальных изменений, в SSMS под администратором выполнить database/install/07_folders_and_purge.sql после 00–06. Web.config и каталог данных остаются прежними; права пула Modify на DataRoot уже должны быть настроены. Ctrl+F5 на index.html. Установочный SQL ничего не удаляет: он создаёт журнал заданий/проверку схемы и разрешает приложению DELETE на storage.UserVaults без отключения FK/db_owner.

## Папки и заметки
Слева текущий относительный путь, На уровень выше, Новая папка и список подпапок. Это навигация по текущему каталогу, ещё не дерево с одновременно раскрытыми ветками. Новая заметка создаётся внутри текущего каталога; читать/редактировать/сохранять можно вложенные .md. Смена папки не очищает открытый редактор; заголовок показывает полный относительный путь, поэтому заметка может оставаться открытой из другой папки. При обычном переключении файла действует прежнее предупреждение несохранённых изменений.
GET vault.ashx?action=list&folder=Работа/Серверы возвращает folder/files/folders; files и folders — полные относительные пути. POST mkdir с name=Работа/Серверы требует существующего родителя, не создаёт цепочку молча. Старый name корневого .md остаётся допустимым. POST create/read/save сохраняют существующий API, но name может включать относительные компоненты через /. Абсолютные пути, обратные слеши, пустые/скрытые/.. компоненты, зарезервированные Windows-имена и reparse points запрещены. Проверяется каждый компонент и граница корня. Лимиты первого этапа: до 16 компонентов, 180 символов относительного пути, 100 в компоненте, 240 полного пути, 500 нескрытых записей одного каталога; заметка до 256 KiB. Другие файлы не показываются как редактируемые заметки.
История всё ещё сохраняется предыдущими .md-копиями без интерфейса восстановления и стабильного ID заметки. Полноценное сопоставление истории с путём/переименованиями остаётся задачей.

## Полное удаление
Только администратор, собственную/административную запись нельзя. Сначала мягко удалить. Новая кнопка явно предупреждает об уничтожении ВСЕХ заметок, вложенных папок, файлов в каталоге владельца, истории и сессий. Ввести точный логин. Новый POST api/admin/purge_user.ashx требует userId,rowVersion,confirmationLogin,deleteFiles=true, сессию и CSRF. Путь не принимается из браузера: только GUID хранилища из storage.UserVaults.
Журнал storage.PurgeJobs: JobId, уникальный TargetUserId, ActorUserId, VaultId, RootHash и Started/RetryRequired/Complete, тип последней ошибки и UTC. Только ID/хеш корня/тип ошибки, не тексты заметок/пароли. Полного UI журнала пока нет: при ошибке идентификатор приходит как errorId; администратор может проверить таблицу в SSMS.
1. SQL фиксирует задание перед удалением. Предварительно проверяются админ, мягкое удаление, логин, RowVersion, связь с GUID и допустимость схемы.
2. Во второй транзакции блокируются админ/цель/задание, повторно проверяются права и связь. Выполняется полный обход двух каталогов для запрета reparse points и лимитов, затем удаляются только DataRoot/vaults/<GUID N> и DataRoot/history/<GUID N>.
3. Только после успешной очистки удаляются сессии, реестр хранилища и учётка; задание Complete фиксируется вместе с этим SQL. При успешном ответе пользователя/реестра/каталогов уже нет. Логин освобождается. Бэкапы, аудит reset и журнал purge не очищаются; безопасное стирание с носителя/удаление внешних копий не обещается.

## Сбои и повтор
SQL и файлы не образуют одну атомарную транзакцию. После подтверждения полного удаления ошибка может оставить ЧАСТИЧНО удалённые файлы. При такой ошибке SQL-удаление учётки/реестра откатывается: мягко удалённый пользователь остаётся в списке, задание Started или RetryRequired. Повторить кнопку после устранения причины; отсутствующие уже удалённые каталоги допускаются. Это продолжение необратимой очистки, не восстановление. Во время удаления используется SQL-блокировка цели/задания, чтобы два запроса этого обработчика не чистили одновременно.
Если процесс оборвался, Started остаётся для повтора. RootHash запрещает продолжать задание на другом DataRoot; не менять корень/реестр при незавершённом удалении. Недоступная БД может помешать записать последнюю ошибку, но первоначальное задание уже сохранено. Потерянный ответ после Complete допускает повтор того же userId: вернётся успешный результат завершённого задания.
Проверка storage.AssertPurgeSchema выполняется AS OWNER только для чтения метаданных и запрещает неизвестные FK-зависимости от Users/UserSessions/UserVaults. При внедрении новых таблиц процедуру/очистку обязательно доработать. FK не отключаются. Старый user_manage purge сохранён для совместимости и по-прежнему не удаляет владельца хранилища; новый UI всегда использует purge_user.
Защита обхода: обычный локальный каталог, контроль ACL, отсутствие недоверенных сторонних писателей. Не добавлять junction/symlink/импорт чужих ссылок. Перед рекурсивным удалением полный preflight, при самом удалении повторные проверки атрибутов без перехода по reparse. Предел 10000 узлов/24 уровня/240 символов пути, бюджет около 20 секунд файловой работы на попытку. Ошибка/лимит не выдаются за успех. Большие неподдерживаемые деревья требуют отдельного доработанного процесса, а не отключения защит. Учётка без хранилища может удаляться без настроенного DataRoot. Незарегистрированные сиротские каталоги после старого неуспешного init не связываются с пользователем наугад.
