## 1. Следующая задача и приоритет инструкций

Первым делом выполнить полную ревизию документации, а не продолжать добавление Markdown-функций. Допустимо несколько последовательных коммитов; цель — законченная согласованная структура, а не ещё одно датированное дополнение поверх противоречивого текста.

Новые требования заменяют прежнее правило «документы только дополнять, старый текст не переписывать». Документацию разрешено переписывать, объединять, переносить и удалять дубли после сохранения уникальных технических сведений. Не терять действующие требования, открытые задачи, ограничения, правила безопасности и реальные результаты проверок. Git сохраняет историю; не нужно превращать актуальные инструкции в архив всех разговоров.

Убрать из актуальной документации повествование «пользователь одобрил/принял/сказал», цитаты из чата, отчёты о согласовании с ассистентом, устаревшие «НОВОЕ», номера этапов как замену предметной структуре и цепочки противоречащих друг другу дополнений. Вместо этого описывать поведение, границы реализации и проверяемые факты. Статусы «реализовано», «ограничение», «планируется», «проверено такими-то тестами» должны иметь основание; редактура не делает экспериментальную функцию готовой.

## 2. Обязательный способ работы

Все изменения проекта ведутся исключительно через коммиты и push в GitHub. Не выдавать локальные инструкции редактирования, патчи в чате, ZIP или скачиваемые файлы за выполненную работу в репозитории. Пользователь получает изменения через безопасное обновление рабочей копии из GitHub. Для работы через connector: найти доступные инструменты, получить их схемы, читать актуальные файлы и запрашивать подтверждение точного payload перед каждой записью. Не считать общее пожелание разрешением любого будущего удаления или иного изменения.

Один коммит — связанный проверяемый этап. Перед заменой файла прочитать его целиком и проверить текущую базу. После push сверять реальные сохранённые файлы и diff; при необходимости — Git blob SHA с проверенным содержимым. Ранее были ошибки переноса: обещанные тесты/документы не попадали в commit, а в списке расширений терялся nativeText.extension. Не повторять это. При неполном ответе инструмента не выдавать его за полный файл и не перезаписывать недочитанный документ.

Не применять reset --hard, git clean, force push; не затирать локальные изменения. Не коммитить DataRoot, настоящие заметки/вложения, бэкапы, секреты, рабочий Web.config и node_modules. Не менять зависимости, lock, SQL, серверный код или browser bundle под видом правки документации. Публикация сайта отдельно от исходников: docs/tools/корень Git не копируются в IIS.

## 4. Целевая организация информации

Предварительная схема, уточняемая после инвентаризации:

- README.md: назначение, поддерживаемая среда, краткие возможности и вход в документацию.
- docs/index.md: единый предметный указатель, без списка датированных дополнений.
- Установка/сборка/обновление/публикация: согласованные рабочие инструкции с безопасными командами. Устранить противоречия first_install, deployment, npm_build, cm6_setup и github_transfer, сохранив необходимые различия.
- Тематические руководства: аккаунты и сессии; файлы/корзина/перенос; рабочая область; редактор/Markdown/свойства/ссылки/таблицы/сноски; граф; темы и DOM/CSS-контракт. Не плодить отдельную инструкцию на каждый патч.
- Архитектура/API/БД: фактический контракт со ссылками на реализацию. ТЗ и будущие решения отделять от реализованного.
- Тестирование: область автоматических и ручных проверок, команды, условия остановки и воспроизводимые чек-листы. Результаты конкретных прогонов не превращать в вечное обещание совместимости.
- Backlog: сохранить уникальные задачи и связи из next_steps, handoff и профильных файлов, убрать дубли/устаревшие статусы после сверки с кодом. Не считать отсутствующий в кратком списке пункт отменённым.
- История изменений: только канонический changelog. В актуальных руководствах оставить описание текущего поведения и ссылку на историю, а не локальные журналы патчей.
- Handoff: один актуальный технический вход для продолжения. Старые передачи после извлечения требований убрать из приоритетной навигации; архивировать только если есть полезный уникальный контекст. Не создавать ещё один лабиринт архивов вместо нормализации.

## 5. Единый changelog

Сейчас уже есть CHANGELOG.md как вход, docs/changelog/README.md как правила и помесячные файлы, например 2026-10.md. Сначала изучить существующую схему, затем привести её к одному образцу, а не создавать конкурирующую историю.

Рекомендуемый единый формат: дата YYYY-MM-DD или реальная версия с датой, затем категории «Добавлено», «Изменено», «Исправлено», «Безопасность», «Удалено» только при наличии записей. Каждая запись кратко объясняет изменение продукта; commit SHA/ссылка служит трассировке, а не заменяет описание. Выбрать один порядок дат, язык, формат заголовков и ссылок для всех файлов. Не выдумывать релизные версии; version 0.5.0 в package.json — идентификатор компонента, не доказанная версия развёрнутого сайта.

Найти историю в README, указателе, handoff, «дополнениях», отдельных файлах этапов и других инструкциях. Сначала перенести уникальные записи с подтверждаемыми датами/коммитами в каноническую историю и сверить полноту, только затем убрать дубли из исходных документов. Не переносить дословно диалоги и длинные отчёты ассистента. Будущие задачи — в backlog; известные текущие ограничения — в тематическую документацию; команды проверки — в тестирование. Неразрешённые противоречия фиксировать явно, не выбирать удобный статус без оснований.

Существующий архив README_2026-10-22.txt и его checksum проверить до изменения политики архива. Для замороженного архива отдельно определить исключение из очистки текста и обозначить его исторический статус; не менять содержимое архива, продолжая называть прежнюю checksum действительной.

## 8. Тесты, безопасное обновление и отчёт

Рабочая копия: D:\project\WebVault. Сначала git status -sb и diff; только на безопасной согласованной базе — git pull --ff-only. При локальных изменениях остановиться, ничего не сбрасывать/не прятать автоматически. Известное локальное восстановление nativeText.extension особенно важно.

Node-команды выполняются из D:\project\WebVault\tools\cm6, не из корня: корневого package.json нет. npm test запускает только 4 перечисленных файла; полный набор — npm run test:all (node run_all_tests.mjs). Runner обнаруживает верхнеуровневые *.test.mjs без shell glob и запускает последовательно; вложенные тесты и браузер не включены автоматически. Старую Windows-инструкцию node --test *.test.mjs не распространять вместо штатного runner.

Для функциональной правки/изменения сборочной цепочки: адресные тесты, полный npm run test:all, после успеха npm run build, затем отдельная публикация bundle и ручная проверка. Каждый шаг только после успеха предыдущего; в PowerShell проверять $LASTEXITCODE. Не игнорировать падения и не ослаблять assertions ради зелёного результата. Не выполнять npm install/ci, не менять lock и не запускать audit fix --force для редакторской правки.

Для чисто документационного commit обязательны проверки ссылок/якорей, существования путей и scripts, полноты переноса, формата Markdown, отсутствия потерянных задач/утекших секретов и непреднамеренного diff исполняемого кода. Не требовать пересборку/публикацию сайта на каждом docs-only этапе. Если полный test:all не запускался или запуск не требуется для конкретного docs-only diff, сказать это прямо, а не писать «все тесты прошли». Команды/скрипты, изменённые вместе с документацией, проверять отдельно; кодовую правку отделять.

В отчёте после каждого push: SHA, список фактически изменённых/перенесённых/удалённых файлов, что проверено и где, что не запускалось, нужна ли сборка/публикация, остаток карты миграции. После всей серии проверить GitHub-содержимое и ссылки заново. Не смешивать модельные тесты, полный Node-набор, сборку, ручные сценарии и совместимость со всеми темами.
