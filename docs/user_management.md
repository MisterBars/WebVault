# Управление пользователями

## Область и границы

Единое руководство по созданию, списку, переименованию и мягкому удалению пользователей; различает старое удаление записи и очистку владельца хранилища. Сведены users.md, ui_and_users.md и прежний user_management.md. Документы, AdminUsersHandler.cs, UserManagementHandler.cs, AccountHandler.cs, SetupStatusHandler.cs, account_features.js и совместимая users.html статически сверены на базе 878c662e2cf81193edaf1337fee5ca902ce4e08d. Новые SQL/IIS/браузерные проверки не запускались. Наличие обработчика не доказывает работоспособность установки или полную регрессию.

Действия администратора над чужой учёткой не следует смешивать с собственным ником/паролем. Администратор управляет пользователями, обычная учётка используется для личных заметок; прямой переход на страницу не заменяет серверную проверку роли. Старые описания пустого workspace или отсутствующего файлового API относятся к ранним этапам, не к текущему сайту.

## Установка и вход

Основная точка входа — index.html. users.html является совместимой переадресацией на index.html?view=users, а не самостоятельной актуальной панелью. Исторические инструкции последовательного открытия auth.html/users.html/workspace.html не подменяют единый интерфейс. Использовать один origin: например, не смешивать localhost и 127.0.0.1 между входом и запросами. Проверять обычного пользователя в отдельном приватном профиле, чтобы не смешивать cookies с административной сессией.

Установку/обновление выполнять по first_install.md: бэкап БД и DataRoot, сохранённые черновики и локальные изменения, только подтверждённо неприменённые SQL-скрипты. Создание основано на 02_auth.sql; жизненный цикл использует 03_user_lifecycle.sql (DeletedUtc datetime2(3) NULL), старый management — 04_user_management.sql (DELETE роли приложения только на auth.Users). Для текущих аккаунтов требуется 06, для purge владельца — 07; это не команда заново применить уже выполненные миграции. Не выдавать пулу db_owner, не отключать FK и не заменять рабочий Web.config шаблоном.

После функционального обновления отдельно опубликовать согласованные файлы сайта и выполнить Ctrl+F5. Эта документационная консолидация не меняет SQL, конфигурацию, код или bundle и не требует публикации.

## Первоначальная настройка администратора

GET api/auth/setup_status.ashx возвращает ok/canSetup, не ключ настройки. Доступность формы требует локального запроса, AdminSetupEnabled=true, ключа длиной не менее 40 символов и отсутствия любых пользователей в auth.Users. Форма скрыта по умолчанию, при ошибке статуса остаётся скрытой и после создания администратора скрывается. Сам setup повторно проверяет условия на сервере: видимость формы не является защитой.

После появления пользователей форма не должна показываться даже при забытом включении; всё равно выключить AdminSetupEnabled и очистить AdminSetupKey. Генерация/установка ключа и проверки setup — в first_install.md и session_policy.md. Не создавать администратора ручной вставкой в БД.

## Список и создание обычной учётки

GET api/admin/users.ashx — совместимый список первых 200 неудалённых пользователей по UserId; хеши, соли и токены не возвращаются, пагинация не реализована. Текущий management-список описан ниже.

POST api/admin/users.ashx принимает JSON login/displayName/password, требует действующую административную сессию, X-WebVault-Request: 1 и X-CSRF-Token из me. Перед вставкой в транзакции повторно проверяются действительность/срок/отзыв сессии, активность, неудалённость и административный статус инициатора.

- Login после Trim: 3–64 символа A–Z/a–z/0–9/подчёркивание/точка/дефис; NormalizedLogin формируется через ToUpperInvariant.
- DisplayName после Trim: 1–100 символов. Создание в AdminUsersHandler проверяет длину, но не имеет явной проверки Char.IsControl, которая есть у rename/profile; не приписывать всем маршрутам одинаковую валидацию без изменения кода.
- Password: 15–128 символов; пароль не обрезается. Для вычисления используется отдельный CreateSlot: один вычисляющий запрос на процесс, занятость даёт 429 server_busy.
- Создаётся только обычная учётка: IsAdmin=0 независимо от переданного isAdmin; активность задаётся схемой. Администратор задаёт начальный пароль и знает его. Автоматический MustChangePassword для первоначального создания не добавлен; обязательный режим включается административным сбросом.
- Успех — 201 с безопасными полями созданного пользователя; нарушение уникальности — 409 login_exists. Нормализованный логин уникален также среди мягко удалённых. DisplayName не уникален.

Создание пользователя не следует считать созданием файлового каталога. Инициализация личного хранилища и файловый API — отдельный путь. Самостоятельная регистрация, управление ролями и восстановление мягко удалённой записи не объявляются реализованными этим API. Не коммитить и не присылать пароли/токены.

## Management API и конкуренция

GET api/admin/user_manage.ashx?includeDeleted=1 возвращает первые 200 записей, включая мягко удалённые; без значения 1 — только неудалённые. Поля включают isDeleted и rowVersion (Base64 от восьми байт SQL rowversion). Пароли/соли/токены в список не включаются.

POST на тот же маршрут принимает JSON:

| action | Поля |
| --- | --- |
| rename | action, userId, rowVersion, login, displayName |
| soft_delete | action, userId, rowVersion |
| purge | action, userId, rowVersion, confirmationLogin |

Требуются административная сессия и оба защитных заголовка. Инициатор/сессия и цель проверяются на сервере с транзакционными блокировками. Инициатор должен быть активным, неудалённым администратором без MustChangePassword. Свою запись и любую административную цель этим модулем менять/удалять нельзя. Неверная Base64/не восемь байт — 400 invalid_row_version; отсутствующая цель — 404 user_not_found; изменившийся RowVersion — 409 user_changed_reload_list. Обновить список и заново проверить данные, не повторять устаревшее изменение вслепую. Вход пользователя тоже может изменить RowVersion: конфликт не обязательно ошибка UI.

Создание остаётся POST users.ashx. Старые GET users и POST user_delete сохранены как совместимые маршруты; новый management-путь не отменяет их серверных проверок. Общие проверки защищённых API находятся в WebApi.cs; AuthHandler сохраняет отдельные вспомогательные функции — их консолидация остаётся задачей рефакторинга, не выполняется документационной правкой.

## Переименование и отзыв сессий

Для обычной неудалённой цели редактируются Login и DisplayName. UserId и пароль сохраняются. Login проходит ту же грамматику/нормализацию; DisplayName — Trim, 1–100 и запрет управляющих символов. Дублирующий нормализованный логин даёт 409 login_exists. Мягко удалённая цель не редактируется: deleted_user_not_editable.

Текущий UserManagementHandler отзывает все сессии цели при административном rename, включая изменение только DisplayName и регистра логина. Прежнее утверждение «одно имя не отзывает сессии» устарело. Это отличается от собственного profile: он сохраняет текущую сессию и отзывает остальные. Политика собственного ника/пароля — в session_policy.md; административный reset — в account_security.md до сведения этой группы.

Новый логин применяется к той же учётке, не создаёт нового владельца/хранилище и не меняет пароль. Отзыв проявляется следующим защищённым запросом; уже показанный экран не исчезает мгновенно.

## Мягкое удаление

Обычную неудалённую цель можно мягко удалить после подтверждения UI. Сервер устанавливает IsActive=0, DeletedUtc/UpdatedUtc в UTC и отзывает все неотозванные сессии в одной транзакции. Повтор management-действия для уже удалённой цели возвращает already_deleted. В обычном списке запись скрывается, при includeDeleted=1 видна.

Запись, логин и данные владельца сохраняются; это не полное удаление персональных данных, не очистка заметок и не корзина файлов. Не восстанавливать удалённую учётку ручным IsActive=1: согласованный маршрут восстановления пока не описан. Передача владения не реализуется мягким удалением.

Совместимый POST api/admin/user_delete.ashx принимает userId без rowVersion, защищён административной ролью/CSRF и запретом себя/администраторов; выполняет мягкое удаление и отзыв сессий, не purge. Не переносить отсутствие rowVersion этого маршрута на новые management-запросы.

## Два разных полных удаления

### Совместимый purge записи

Старый POST user_manage.ashx с action=purge требует мягко удалённую неактивную цель и точный текущий confirmationLogin (Ordinal, без угадывания регистра/пробелов). Ошибки: soft_delete_first, confirmation_login_mismatch. В одной SQL-транзакции удаляет auth.UserSessions и auth.Users; при ошибке откат, FK не отключаются. SQL FK-конфликт возвращает 409 user_has_dependencies. Наличие таблиц notes блокируется vault_cleanup_not_implemented.

Этот маршрут не обходит файловые каталоги, не очищает storage.UserVaults и не является универсальным поиском зависимостей. Владельца зарегистрированного хранилища нельзя удалять им в обход согласованной очистки: FK и другие защиты не отключать. Старый UserId не назначать вручную новому пользователю; после успешного удаления записи нормализованный логин освобождается, новая учётка имеет новый ID.

### Purge владельца с файлами

Для текущей очистки владельца используется отдельный POST api/admin/purge_user.ashx с userId,rowVersion,confirmationLogin,deleteFiles=true. UI должен явно предупреждать об удалении заметок, папок, истории и сессий. Требуются предварительное мягкое удаление, администратор, точный логин, CSRF и проверки версии/владения; путь не принимается из браузера.

Процедура, PurgeJobs, RootHash, ограничения обхода/reparse, частичные ошибки и повтор описаны только в folders_and_purge.md. SQL и файлы не образуют одну атомарную транзакцию; ошибка может оставить частично удалённые файлы. Не копировать обещание SQL-отката старого purge на файловую очистку. Аудит reset, журнал purge, бэкапы и внешние копии не удаляются автоматически; гарантированное стирание не заявлено.

## Воспроизводимые проверки

Все пункты — план на отдельных тестовых учётках/копиях данных, не отчёт об успешном прогоне. Не испытывать purge на единственной копии настоящих заметок. Сценарии авторизации, CSRF, HTTPS, временного пароля и текущей сессии дополнительно выполнять по session_policy.md.

1. Администратор видит список и создаёт обычного пользователя; безопасные ответы не показывают пароли/хеши/соли/токены. Передача isAdmin=true не создаёт администратора. Новый пользователь входит/выходит в независимом профиле.
2. Дублирующий логин, включая другой регистр и логин мягко удалённой записи, отклоняется; невалидные login/DisplayName/длина пароля отклоняются. Пагинация не обещается сверх 200 записей.
3. Без сессии GET/POST получают 401, обычный пользователь в административном API — 403; отсутствие/неверный CSRF, чужой Origin и недопустимый удалённый HTTP не обходят защиту. Прямой переход на UI не даёт прав.
4. Переименование не меняет UserId/пароль/владельца; новый логин работает, старый перестаёт. Все сессии цели отозваны также при изменении только DisplayName. Собственный ник отдельно сохраняет текущую сессию.
5. Некорректный/устаревший rowVersion, конкурентный вход/изменение и SQL-ошибка не перезаписывают чужие новые данные и не дают частичной SQL-операции. После 409 повтор только с новым списком.
6. Мягкое удаление требует подтверждения, скрывает цель из обычного списка, показывает её при includeDeleted=1, запрещает вход; прежняя сессия получает 401 следующим запросом. Логин занят, файлы этим действием не удалены.
7. Себя и любую административную цель нельзя переименовать/удалить; удалённая цель не редактируется. Совместимый user_delete остаётся мягким маршрутом и не получает ложного обещания rowVersion.
8. Старый purge без мягкого удаления или с неверным логином запрещён; при notes/FK-зависимостях нет частичного удаления записей. Только поддержанная учётка без зависимостей удаляется транзакционно; логин допускает новую учётку с новым ID.
9. Purge владельца проверять отдельным сценарием folders_and_purge.md: соседние каталоги нетронуты, ошибку/частичную очистку не выдавать за успех, повтор задания не удаляет данные нового пользователя с повторно занятым логином.
10. Setup скрыт после создания администратора до/после logout/reload; на новой тестовой пустой установке доступен лишь при корректном локальном включении/ключе. Ключ не возвращается, после установки выключен и очищен. Старые setup/login/me/logout и ASP.NET/SQL health работают.
11. Единая навигация показывает доступный раздел, имя, выход и диагностику; административные действия не теряют несохранённую заметку текущей учётки. Существующие файлы/свойства/сохранение не объявляются проверенными по одному успеху создания пользователя.
