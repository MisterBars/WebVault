# Переименование и два режима удаления

Статус: код подготовлен, выполнение в IIS и новой миграции ещё не подтверждено. Дополняет users.md и ui_and_users.md; прежний запрет полного удаления заменяется описанным ниже ограниченным режимом.

## Обновление
Сделать бэкап WebVault. Получить код, выполнить 03_user_lifecycle.sql если ещё не применён, затем database/install/04_user_management.sql под администратором SSMS. 04 выдаёт webvault_app право DELETE только на auth.Users. Перезапустить/обновить страницу users.html с Ctrl+F5. Web.config не меняется.

## Интерфейс
У обычных неудалённых пользователей: Переименовать и Мягко удалить. В форме редактируются логин и отображаемое имя. У мягко удалённых, видимых при переключателе Показывать также мягко удалённых: Удалить навсегда. Полное удаление требует ввода точного текущего логина. Себя и любую административную запись менять/удалять этим модулем нельзя. Восстановление пока не реализовано.

## API
GET api/admin/user_manage.ashx?includeDeleted=1 — список первых 200 записей, включая мягко удалённые; без 1 показываются только неудалённые. Добавлены isDeleted и rowVersion (Base64 от SQL rowversion).
POST на тот же маршрут, JSON:
- rename: action, userId, rowVersion, login, displayName;
- soft_delete: action, userId, rowVersion;
- purge: action, userId, rowVersion, confirmationLogin.
Для POST требуются действующая административная сессия, X-WebVault-Request и X-CSRF-Token. Проверки выполняются на сервере; целевой пользователь блокируется в транзакции. Изменившийся RowVersion -> 409 user_changed_reload_list: обновить список и проверить данные заново. Вход пользователя также меняет его RowVersion, поэтому конфликт может быть ожидаемым.
Создание остаётся POST api/admin/users.ashx. Старые users GET и user_delete POST сохранены для совместимости; новый UI использует user_manage для списка/изменений.

## Переименование
Тот же UserId, пароль не меняется. Нормализованный логин уникален, включая мягко удалённые записи. Изменение логина (в том числе только регистра отображения) отзывает все старые сессии. Изменение только DisplayName не отзывает их. Мягко удалённые не редактируются.

## Мягкое удаление
IsActive=0, DeletedUtc и UpdatedUtc устанавливаются в UTC, все сессии отзываются. Запись/логин сохраняются. Не является полным удалением персональных данных.

## Полное удаление: текущие границы
Только после мягкого удаления и при IsActive=0. Транзакционно удаляются все auth.UserSessions целевого пользователя и затем auth.Users. При ошибке откатывается вся транзакция. Логин освобождается, старый UserId никогда не назначается вручную новому пользователю.
Сейчас модуль заметок отсутствует, поэтому это удаление только учётной записи и её сессий. Файловые каталоги не удаляются и не обходятся. При наличии видимых приложению таблиц в схеме notes операция блокируется vault_cleanup_not_implemented, пока не будет разработан полноценный регламент очистки хранилищ. Это предохранитель текущего этапа, не универсальный поиск файлов/зависимостей; при внедрении хранилищ его обязательно заменить проверкой владения и согласованным процессом очистки. Ограничения FK также блокируют удаление (user_has_dependencies), никакого отключения FK или произвольного каскада нет. Бэкапы, журналы и внешние копии не очищаются; не обещать гарантированное стирание данных.

## Проверки
- [ ] Сохранены создание, вход, навигация и скрытие setup.
- [ ] Переименование DisplayName не меняет UserId/пароль.
- [ ] Новый логин работает, старый перестаёт работать, сессии отозваны.
- [ ] Дублирующий логин -> 409 login_exists.
- [ ] Конкурентное изменение -> 409, не перезапись.
- [ ] Мягкое удаление запрещает вход, запись видна при переключателе.
- [ ] Полное удаление без предварительного мягкого запрещено.
- [ ] Неверный confirmationLogin запрещает purge.
- [ ] После purge записи и сессий нет, логин можно создать заново с новым UserId.
- [ ] Администратор/сам пользователь защищены сервером.
- [ ] Без сессии/административных прав/CSRF изменения запрещены.
- [ ] При запрете зависимостей/ошибке транзакция не удаляет часть данных.
