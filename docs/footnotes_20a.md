Это чистый resolver событий, а не regexp-parser Markdown: следующий этап должен получать definitions/references из синтаксического разбора, исключая code, escape, YAML и другие неактивные контексты. Модель сама не распознаёт [^label], ^[body], отступы четырёх пробелов или разметку абзацев. Поддержка этих синтаксических форм и их отображение ещё НЕ реализованы этим этапом.

## Контракт
resolveFootnotes принимает definitions={label,body,from,to} и references={kind:'named',label,from,to} либо {kind:'inline',body,from,to}. Возвращает каталог первых определений, ссылки с status, использованные notes и diagnostics. from/to — исходные UTF-16 смещения с исключённой правой границей; существующий текст не модифицируется. Body сохраняется как предоставленная строка, включая форматирование/переводы строк; его Markdown-разбор и отображение — следующий слой.

Нумерация начинается с 1 по первому разрешённому упоминанию в исходнике, не по порядку определений. Повторные named references разделяют один номер, каждое получает occurrence и свой диапазон для будущих обратных переходов. Одинаковые inline-body в разных местах создают разные сноски. Неиспользованные определения и неизвестные ссылки номера не занимают.

Метки буквальные, case-sensitive Unicode, без пробелов/скобок/control chars, до 128 UTF-16 единиц. Для каталога используется Map, включая метки вида __proto__. Первое определение по исходному from имеет приоритет; дубликат получает diagnostic. Неизвестные, невалидные и превышающие лимиты события остаются явно unresolved/invalid/limit; renderer обязан сохранять для них исходник, а не удалять содержимое.

По умолчанию maxNotes=512 и maxReferences=2048; это ограничение модели, не изменение глобальных лимитов WebVault. Пересекающиеся source reference events отклоняются — вложенные inline footnotes этим контрактом не объявлены поддержанными. Internal key не является безопасным DOM id: будущему renderer нужны собственные идентификаторы на основе номера/контекста, не вставка произвольной метки в HTML.
