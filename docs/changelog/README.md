# Как вести историю изменений

[CHANGELOG](../../CHANGELOG.md) · [Текущий README](../../README.md) · [Задачи](../next_steps.md)

## Назначение файлов

| Файл | Что в нём хранить |
| --- | --- |
| README.md | Назначение, краткое актуальное состояние, установка/ограничения верхнего уровня и навигация. Не дневник патчей. |
| CHANGELOG.md | Вход в историю: ссылки на месяцы и последние значимые состояния. |
| docs/changelog/YYYY-MM.md | Каноническая история принятых изменений: дата, смысл для пользователя, коммит, существенные ограничения. |
| docs/changelog/archive | Замороженные исходные документы/журналы, чтобы ничего не потерять при реорганизации. Не показывать их пользователю сайта автоматически. |
| docs/next_steps.md | Задачи и будущие требования. Существующие пункты не переписывать/не удалять; приёмку и уточнения добавлять датированно. |
| Профильные инструкции | Как работает функция, установка, проверки и ограничения. Не копировать весь changelog в каждую инструкцию. |
| docs/theme_contract.md | Актуальная карта DOM/CSS/токенов и собственных элементов для адаптации тем. |
| docs/theme_compatibility.md | Исторические уточнения оформления и границы совместимости; поздний контракт имеет приоритет. |

## Правила следующего комплекта

1. До правки читать актуальную базу. Отделять код, bundle, установленный сайт и приёмку.
2. Кандидат и инструкция проверки принадлежат технической документации; changelog не должен выдавать кандидата за принятый релиз.
3. После приёмки добавить краткую пользовательскую запись в соответствующий месяц. Сохранить существенный известный дефект и его последующее исправление, не переписывать историю задним числом.
4. Изменения DOM/селекторов/переменных/состояний отражать в актуальном контракте тем; совместимость произвольной темы проверять отдельно.
5. README менять только при изменении краткого состояния/навигации, а не при каждом локальном тесте.
6. Давать одну связанную проверку и готовые команды/название коммита. Для исходников от пользователя — один текстовый JSON-дамп с путями, без секретов и реальных заметок.
7. Не назначать версии по номеру npm-пакета автоматически: идентификаторы сборки компонентов и релиз установленного сайта различаются.

## Будущий экран истории на сайте — только план

Пункт «История изменений» в настройках должен читать локально поставляемые публичные данные установленного комплекта, а не live GitHub и не папку .git. Технические архивы, handoff, локальные пути, секреты и содержимое личных заметок в публичную ленту не включать.

При реализации определить генерацию безопасной публичной ленты из принятых записей и включение её в src/WebVault.Web при сборке/публикации. docs/корень Git не публиковать в IIS. Не исполнять HTML/JS из журнала; отображать контролируемый текст или безопасное подмножество Markdown. Показывать версию/дату установленного сайта, а не автоматически последнюю ветку main. Ни генератор ленты, ни API, ни меню этим документационным комплектом не реализованы.
