Документы и backlog можно переписывать, объединять и переносить после сохранения уникальных требований, задач, ограничений и подтверждённых технических сведений. Правило «только дополнять» не действует. История Git не заменяет проверку сохранности при миграции.

## Единый образец

Язык записей — русский. В месяце даты идут от новых к старым; одна секция на дату. Дата в формате YYYY-MM-DD, внутри категории в порядке: Добавлено, Изменено, Исправлено, Безопасность, Удалено. Пустые категории не добавлять. Внутри категории — краткие понятные пункты о нововведениях и правках, существенная граница и ссылка на подтверждающий коммит, если он установлен.

```markdown
## YYYY-MM-DD

### Исправлено

- Описание изменения и существенного ограничения. Коммит: [SHA](ссылка-на-коммит).
```

Это шаблон, не настоящая дата/версия/запись. Не назначать релизные версии по номеру npm-компонента или условному номеру этапа. Реальную версию использовать только при наличии подтверждённого релиза и даты; версия установленного сайта, исходник main и bundle — разные состояния.

В тексте записей и подписях источников не использовать внутренние номера этапов/патчей, имена комплектов и ID задач вместо описания изменения. Связи между исправлениями объяснять предметно. Старые идентификаторы сохраняются при необходимости в backlog, профильных руководствах, временной матрице и исторических оригиналах. Имена файлов внутри закреплённых Git-URL не переименовывать ради удаления номера; SHA коммитов и подтверждённые реальные версии не являются этапной нумерацией.

Дата коммита означает дату записи исходника, не автоматически дату внедрения или браузерной проверки. При разных датах явно указать, что именно датируется. Запись в changelog не означает полной регрессии, публикации сайта или совместимости со всеми темами/плагинами.

Для уникальной истории без установленной даты сначала зафиксировать источник и нерешённый вопрос в матрице переноса. Не помещать её в произвольный месяц и не удалять оригинал, пока место канонической недатированной записи или дата не определены. Не придумывать SHA; известный короткий SHA разрешить и проверить перед созданием ссылки.

## Содержание и статусы

- Описывать дату и суть изменений продукта или процесса, а не кто что одобрил. Не включать одобрения, цитаты переписки, разговорные статусы, локальную синхронизацию и длинные отчёты согласований.
- Сохранять существенный дефект и его последующее исправление отдельными историческими фактами. Уточнение ошибочного факта допустимо с основанием; косметическая редактура не превращает кандидата в готовый релиз.
- Отдельный кандидат/эксперимент допустимо описать только с явным статусом и основанием; инструкции его проверки принадлежат тестированию/профильному документу. Сам коммит не доказывает выполненные тесты.
- Будущие работы переносить в backlog, известные текущие ограничения — в профильное руководство, команды и процедуры — в тестирование/сборку. Существенную историческую границу изменения кратко сохранить и в записи.
- Подробные исторические результаты тестов хранить с исходной базой, областью и источником в документации тестирования; до её сведения допустимо временное сохранение в существующем реестре миграции. Не превращать реестр в постоянный журнал. Модельные тесты, Node-набор, build и браузер различать; отсутствие вывода не считать успехом. Не переносить старые числа на новый HEAD.
- Изменение DOM/селекторов/переменных/состояний отражать в текущем контракте тем. README менять при изменении состояния/навигации, не как дневник каждого патча.

## Порядок миграции и проверки

1. Полностью прочитать источник и актуальный канонический changelog. Неполный ответ инструмента не считать полным файлом.
2. Выделить уникальные исторические события, технические ограничения, требования, задачи и процедуры. Для каждого указать целевое место; сохранять ID задач и связи вне ленты изменений.
3. Сверить даты, commits и статусы по источникам/реализации; неразрешённые противоречия оставить открытыми.
4. Сначала записать уникальную историю в каноническое место. Проверить сохранённое GitHub-содержимое и соответствие матрице переноса.
5. Только после проверки убрать исторические дубли из актуальных руководств. Для раздельных коммитов временный дубль допустим, потеря оригинала до проверки — нет.
6. Проверить ссылки/якоря/пути, формат, отсутствие потерянных требований/задач и непреднамеренного кодового diff. После всей серии повторить общий аудит.

Существующие месячные файлы пока могут не соответствовать образцу: утверждение правил само по себе не означает завершённую миграцию их записей. Проверенные новые правила применяются при последовательной нормализации файлов, без массового удаления старых данных.

## Замороженный архив

[README_2026-10-22.txt](archive/README_2026-10-22.txt) — исторический снимок с устаревшими статусами и исходными ссылками относительно прежнего расположения. Он исключён из очистки разговорных формулировок и исправления старых ссылок; не использовать его как текущую инструкцию и не публиковать автоматически на сайте.

Рядом хранится [SHA-256](archive/README_2026-10-22.sha256). Перед изменением политики архива сверять хеш исходных байтов Git blob, не копии после CRLF/LF-конвертации или пересохранения редактором. Чтение checksum не равно вычислению и подтверждению хеша. В этой редактуре архив и checksum не меняются; побайтовое совпадение не объявляется проверенным. Изменённый архив нельзя продолжать называть побайтно прежним с прежней действительной checksum.

## Будущий экран истории — требования, не реализация

CHANGELOG-UI-01/02/03: пункт настроек должен читать локально поставляемую безопасную публичную ленту установленного комплекта, не live GitHub/CDN и не .git. Определить генерацию из канонической истории и включение в src/WebVault.Web при сборке/публикации. Не включать технические архивы, handoff, локальные пути, секреты и личные заметки; docs/корень Git не публиковать в IIS.

Не исполнять HTML/JS из истории: контролируемый текст или безопасное подмножество Markdown. Показывать версию/дату установленного сайта, не автоматически HEAD main. Генератор, API и меню этим документом не реализованы; требования сохраняются в backlog.

## Работа с изменениями

Перед записью читать актуальную базу, подтверждать точный GitHub payload; после push сообщать SHA, состав и фактические проверки. При необходимости получить исходники от рабочей копии использовать один текстовый JSON-дамп с путями, без секретов и реальных заметок, не ZIP и не множество вложений. Не запрашивать повторно уже предоставленные данные только из-за обрезанного ответа коннектора.

Исходники и документы просматривать в VS Code по [рабочей инструкции](../github_transfer.md). Выбор редактора не является зависимостью сайта. Docs-only не требует пересборки сайта; не заявлять тесты/PowerShell/браузер выполненными без запуска.
