# WebVault — техническое задание v0.1

Исходная дата требований: 2026-10-19. Документ определяет назначение и долгосрочные требования, не текущий статус реализации и не версию установленного сайта. Часть возможностей уже описана в предметных руководствах; оставшиеся работы и границы проверки — в [backlog](../next_steps.md), навигация — в [указателе](../index.md), история — в [changelog](../../CHANGELOG.md). Полное выполнение этого ТЗ не заявлено.

## 1. Назначение
Автономное приложение заметок с веб-интерфейсом. Первое размещение — сайт IIS на рабочем ПК Windows 7 без интернета; последующее — сервер локальной сети для нескольких пользователей. Не полная копия Obsidian.

## 2. Ограничения среды
- Классический ASP.NET/.NET Framework, C#, обработчики .ashx, общие классы App_Code.
- HTML/CSS/JavaScript; библиотеки локально в поставке, без CDN.
- MS SQL Express 2014 — основная служебная БД.
- На рабочем ПК не требовать ASP.NET Core, Node.js, npm, Docker или новых системных компонентов; сборочные инструменты могут работать на отдельном подходящем ПК.
- Уточнённая целевая среда: .NET Framework 4.5 и Firefox 113. Совместимость компилятора C#/IIS/библиотек и конфигурации конкретной установки проверяется отдельно.
- Access — возможная будущая альтернатива служебной БД для локального использования, не текущий второй провайдер.

## 3. Архитектура и данные
Браузер → API .ashx → C#-сервисы → SQL Server и файловая система. Markdown-файлы — источник истины текста; БД хранит пользователей, сессии, настройки, привязку хранилищ и восстанавливаемые индексы.
Личные файлы вне публичной папки сайта, чтение заметок/вложений только через API с проверкой доступа. SQL должен быть изолирован в слое доступа, не распределён по обработчикам; это архитектурное требование, не отчёт о завершённом рефакторинге. Будущий Access не должен требовать переписывания файловой логики, второй провайдер сейчас не нужен.

## 4. Пользователи
- Одноразовая инициализация первого администратора с запретом повторного запуска.
- Вход/выход, собственная смена пароля, тайм-аут сессии и блокировка учётки.
- Самостоятельная регистрация с разрешением/запретом администратора остаётся требованием, не обещанием действующего UI.
- Пароли не хранятся открыто. Текущая политика хеширования, сессий и административного временного пароля — в [session_policy.md](../session_policy.md); наличие контракта не доказывает безопасность конкретной установки.
- Личное хранилище и настройки; владелец из серверной сессии, не userId запроса. Создание учётки само по себе не означает инициализацию файлового каталога.
- Администратор приложения не получает автоматический просмотр чужих заметок через UI.
- Общие папки/совместное редактирование не входят в первую версию.
- Авторизация не защищает от администратора ОС с доступом к диску. Шифрование хранилища — отдельная будущая задача.

## 5. Хранилища
Каталоги vaults/<VaultId>, history и backups находятся в отдельном каталоге данных; идентификаторы не зависят от логина. Это требование организации данных, не замена текущего файлового регламента.
Русские имена, новые заметки UTF-8, исходная структура импортируемых папок, неизвестная разметка/YAML без потерь. Конфигурация WebVault отдельно от .obsidian; .obsidian не исполнять и автоматически не перезаписывать.
Начальный способ импорта — подготовленная копия каталога с индексацией; браузерный ZIP был дальнейшим направлением исходного плана. Актуальный описанный импорт/экспорт и ограничения — [note_transfer.md](../note_transfer.md), не утверждение об отсутствии ZIP сейчас.

## 6. Основные функции
Дерево файлов/папок, создание/открытие заметок, Markdown-редактор/предпросмотр, ручное/автоматическое сохранение, rename/move, удаление с восстановлением, поиск по названию/тексту, загрузка/просмотр вложений.
Состояния записи: изменено/сохраняется/сохранено/ошибка/конфликт. Ошибка не очищает редактор; перед заменой сохраняется предыдущая версия. API проверяет версию/хеш. Конфликт не перезаписывается молча: актуальный текст либо конфликтная копия. История версий не бэкап: нужны согласованное резервирование БД/файлов и проверка восстановления.

## 7. Совместимость с Obsidian
Базовый объём: .md, YAML frontmatter, Markdown-ссылки, [[Заметка]], пути/подписи wiki, изображения/вложения, сохранность неизвестных блоков. Неоднозначные ссылки требуют выбора.
Дальнейший объём исходного плана: подсказки, backlinks, встраивания, headings/blocks, обновление ссылок после rename, редактор свойств, шаблоны/периодические заметки. Наличие пункта в этом перечне не означает его отсутствие сейчас: статусы — в backlog/руководствах.
Не гарантируются Obsidian-плагины, Dataview/DataviewJS, Templater, Canvas и произвольный JS заметок. Неподдерживаемое сохраняется текстом. Проверки на безопасной копии реального vault; личные заметки не коммитить.

## 8. Темы
Требование: серверный каталог пакетов, установка/обновление администратором, manifest.json/theme.css/локальные ресурсы. Личные тема/светлый-тёмный режим/акцент, возврат к встроенной. Документированные CSS-переменные; произвольные Obsidian-темы требуют адаптации и не автоматически совместимы. Без обязательных внешних шрифтов/изображений. Наличие аудита темы не означает готовый менеджер пакетов.

## 9. Индивидуальные настройки
В БД с пользователем: оформление/шрифт/размер/межстрочный интервал, переносы/отступы, autosave, панели/размеры, стартовая заметка, горячие клавиши, включённые расширения/параметры.
Workspace/вкладки отдельно от общих предпочтений. Браузерное хранилище не единственный источник; системная конфигурация отдельно от пользовательской.

## 10. Расширения
После стабилизации ядра: администратор ставит пакеты, пользователь включает доступные и сохраняет личные параметры. Manifest с ID/версией/совместимостью API; безопасный запуск без расширений.
Начальный API: команды/кнопки/панели, события открытия/сохранения, проверяемые операции заметок, собственные настройки. Без произвольных серверных DLL/команд ОС и обещания совместимости готовых Obsidian-плагинов. Сторонний JS доверенный; декларация разрешений не изоляция.

## 11. Безопасность
Владелец проверяется во всех операциях, включая поиск/вложения/историю/бэкапы. Пути ограничены корнем, обход запрещён; папка данных не публикуется. Защита изменяющих запросов от CSRF, Markdown без исполнения встроенных скриптов, параметризованный SQL. Секреты/реальные данные/локальная конфигурация не в Git. Перед сетевым размещением проверить HTTPS/cookies, не ограничиваться видимостью интерфейса.

## 12. Приёмка первой стабильной версии
Критерии ниже — требования к проверке, не отчёт об успешном прогоне:
- Полная автономная работа.
- Два пользователя имеют раздельные заметки/настройки; прямые запросы не обходят доступ.
- Создание/сохранение/reopen/восстановление удалённой заметки.
- Конфликт двух вкладок без потери текста.
- Вложения только владельцу.
- Поиск и базовые ссылки.
- Личный выбор темы не влияет на другого пользователя.
- Реальное восстановление файлов и БД из бэкапа.
- Инструкции локального и сетевого размещения.
