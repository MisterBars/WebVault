# Навигация и жизненный цикл пользователей

## Статус
Предыдущий модуль создания пользователей и серверный запрет административного API проверены пользователем дома. Этот комплект: код подготовлен, миграция и новый интерфейс ещё не проверены.

## Обновление
1. Сделать резервную копию БД перед изменением схемы.
2. Получить файлы проекта с сохранением локальных изменений.
3. До использования нового API выполнить database/install/03_user_lifecycle.sql в SSMS под администратором. Добавляется auth.Users.DeletedUtc datetime2(3) NULL; данные не удаляются.
4. Убедиться, что AdminSetupEnabled=false и AdminSetupKey пустой после создания администратора.
5. Обновить страницу с очисткой кеша (Ctrl+F5), открыть auth.html или index.html.

## Разделение интерфейса
- Администратор после входа переходит в users.html. Эта учётная запись предназначена для управления, а не личных заметок.
- Обычный пользователь после входа переходит в workspace.html. Пока это явно обозначенная заготовка, редактора и личных настроек нет.
- Общая навигация: свой раздел, имя пользователя, выход, диагностика. Без входа — кнопки входа и диагностики.
- Прямой переход обычного пользователя в users.html перенаправляет в личный раздел, но безопасность административных операций по-прежнему проверяется сервером.
- Перенаправление администратора из workspace — интерфейсное правило, не защита файлов: файлового API ещё нет.

## Первоначальная настройка
GET api/auth/setup_status.ashx возвращает только canSetup. Форма hidden по умолчанию; появляется лишь при локальном запросе, включённой настройке, ключе не короче 40 символов и отсутствии любых пользователей в БД. После успешного создания форма скрывается сразу. При ошибке статуса остаётся скрытой. Сам setup по-прежнему повторно проверяет условия на сервере. Ключ не возвращается.
После существующего администратора форма не показывается даже если настройку забыли выключить; это не отменяет ручное выключение и очистку ключа. Инструкция генерации и установки: first_install.md.

## Удаление
POST api/admin/user_delete.ashx, JSON userId, обычные заголовки X-WebVault-Request и X-CSRF-Token. Только действующий администратор. Собственную запись и любые административные записи удалять запрещено.
Транзакционно: IsActive=0, DeletedUtc=UTC, UpdatedUtc=UTC; все неотозванные сессии пользователя получают RevokedUtc. Список users исключает DeletedUtc IS NOT NULL. Запись остаётся в БД; логин не переиспользуется. Пароли/соли в ответ не возвращаются.
Это мягкое удаление, не физическое уничтожение персональных данных. Будущие заметки также не должны удаляться этим действием. Восстановление, просмотр удалённых, окончательное уничтожение и передача владения пока не реализованы. Не делать ручное IsActive=1 для удалённых записей: восстановление требует отдельной согласованной операции.

## Проверки
- [ ] Выполнена миграция 03 без ошибок.
- [ ] Создание обычного пользователя по-прежнему работает.
- [ ] Вход администратора ведёт в users; личной учётки — в workspace.
- [ ] На всех страницах есть навигация и выход.
- [ ] После создания администратора форма setup скрыта до/после выхода и обновления.
- [ ] На новой пустой установке с корректным ключом и включением форма доступна.
- [ ] Удаление требует подтверждения и убирает обычного пользователя из списка.
- [ ] Удалённый пользователь не входит; его ранее открытая сессия получает 401 при следующем защищённом запросе. Уже показанная страница не исчезает автоматически.
- [ ] Прямой запрос удаления администраторов/себя запрещён; обычный пользователь получает 403.
- [ ] Удалённый логин остаётся занят.
- [ ] ASP.NET/SQL диагностика работает после обновления.
